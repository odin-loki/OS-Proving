# OS-Proving

A proving and formal verification effort for Linux and FreeBSD / HardenedBSD (and the KDE code that runs on them).

The goal is a set of functions from real operating-system code, each carrying a stated contract and an honest label of how strongly that contract is established. The work is aimed at buyers who check claims (for example the US Department of Defense and its contractors), so every claim carries one of the labels below and the counts are always generated by script from the data in this repository.

Status on 13 November 2026: **annotation verification and repair complete through round 20 (hand-fix waves 1 to 3); the first proving tier (24,825 functions) has been run through the prover; its follow-up phases (second bit-vector pass, independent replay, mutation test, contract strength, audit sample) and the large random-sample audits are next.** Start with [docs/ASSURANCE_STATEMENT.md](docs/ASSURANCE_STATEMENT.md) (what is and is not proved, comparison with seL4, next steps), [docs/ERRORS_FOUND.md](docs/ERRORS_FOUND.md) (every error class with counts), [docs/METHOD.md](docs/METHOD.md) (how it works), [docs/HISTORY_DEAD_ENDS_AND_LESSONS.md](docs/HISTORY_DEAD_ENDS_AND_LESSONS.md) (what we tried and why) and [data/errors/README.md](data/errors/README.md) (the error dataset).

## What "proved" means here

Every function has exactly one label. Only the first two may be called proved. Labels are never merged in any summary.

| Label | Meaning |
|---|---|
| **PROVED** | Machine-checked by Frama-C/WP (Why3 with Alt-Ergo, Z3, CVC5): the proof was accepted, with no unstated assumption. |
| **PROVED-ASSUMING** | As PROVED, but it assumes listed preconditions on pointers and memory. The assumption is stored with the result. |
| **BOUNDED** | Bounded model check or exhaustive test within stated bounds. |
| **TESTED** | Passed random and edge-value runtime checks. |
| **REVIEWED** | Passed mechanical checks and a second-model review. **Not proved.** |
| **REJECTED / UNCHECKED** | Everything else. Not offered. |

Tag names in the status tables: `verified` means REVIEWED at best, not proved.

## Where it stands

### 1. Mined annotations (all 1,135,593 functions)

Linux, FreeBSD / HardenedBSD and KDE functions were annotated by language models (a one-line summary, a prose contract and, for scalar functions, a formal contract). Those annotations were checked mechanically, tested, reviewed by a second model, and repaired in rounds. The final table:

| Tag | Functions |
|---|---|
| verified (reviewed, **not proved**) | 527,395 |
| unchecked | 547,342 |
| rejected | 60,479 |
| dropped (not a real function) | 377 |

About 3,000 functions still need hand work after wave 3 (1,169 reviewer disagreements, 1,202 not yet reviewed, 300 still rejected), and 59,010 driver-glue functions were never attempted. A hand pass showed that mechanical and Frama-C checks alone missed real prose errors, and that most reviewer disagreements were real (the reviewer was right on roughly 70 to 90 per cent of its claims). So `verified` is a lead, not an assurance; the random-sample audits put a measured error rate on it.

### 2. Machine proving (core tier, 24,806 functions processed)

Function kinds with the best chance of a proof: arithmetic and bit helpers, bitmaps, allocators, reference counts, ring buffers, lists, locks, parsers, error paths and init/teardown code.

| Label | Functions | Share |
|---|---|---|
| PROVED | 2,388 | 9.6% |
| PROVED-ASSUMING | 3,467 | 14.0% |
| contract only (not proved) | 2,982 | 12.0% |
| contract shown **false** by the prover | 2,148 | 8.7% |
| proof attempt failed | 1,957 | 7.9% |
| did not build | 11,730 | 47.3% |

5,855 functions (23.6%) are proved. The largest loss is code that does not build in isolation (C++ sources, missing kernel headers, FreeBSD sources whose build flags had to be reconstructed). Best kinds: bitmask 71%, arithmetic helpers 30%, bitmaps 28%. Weakest: list operations 4%, reference counts 10%, allocators 11%, ring buffers 11%. The 2,148 functions whose mined contract the prover refuted are a finding in themselves: those contracts were wrong.

Proved results carry assumptions that must be disclosed with them: stub headers assumed empty, callees without a specification, pointers modelled as disjoint objects, and the bit-vector path uses an uncertified SAT solver. See `data/proving/core/summary.md` for the full per-kind and per-assumption tables.

### 3. Not done yet

* The core tier's follow-up phases (second bit-vector pass, independent replay of every proof, mutation test, contract strength, the 400-function audit sample) were interrupted when the disk filled and are being rerun.
* The independent audit of proved statements, the mutation test on a sample of proved functions, the reproducibility script and the assurance case ([plan](docs/plan/lib/code-mined/SELLABLE_PLAN.md), stages S5 and S6).
* A legal review of the licensing of the derived data (see [LICENSING.md](LICENSING.md)).
* Driver glue (about 322,000 functions) depends on hardware and concurrency that proofs here cannot model, so most of it can only reach BOUNDED or TESTED.

## What is deliberately not here

* **No third-party source code.** No Linux, FreeBSD or KDE source is copied. Records name the upstream file and line range, so you fetch the original from upstream. The unit files and source slices used during the work were removed.
* **No credentials.** Nothing in this repository contains an API key.
* File paths inside the records start with `/home/odin/pbsd-ref/linux/` (the working copy of the kernel tree used during the work). Read them as paths relative to the upstream tree.

## Tooling used

Frama-C 33 with WP and Why3; Alt-Ergo, Z3 and CVC5; CBMC 5.95; models served through Morph (GLM-5.3 Flash for repair, DeepSeek V4.1 Flash for review and repair) and Claude models for the hardest cases and for review. The scripts need WSL (Ubuntu) and a private opam root for the prover versions pinned in `docs/plan/lib/code-mined/pilot/`.

## Resuming

The proving run is resumable: finished units are skipped. The staged per-unit results in `data/proving/core/units/` are the saved state; restore them into the run directory, then start the watcher (`docs/plan/lib/code-mined/pilot/watch_core.sh <workers>`). Repair and review stages resume from their `done.keys` files in `data/results/`.
